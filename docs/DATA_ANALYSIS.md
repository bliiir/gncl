# Data analysis: signal inventory

Generated by `python -m gncl.analysis`. Every number measured, not estimated.

Ground truth = the 21 BookIT<->HubSpot pairs locked by exact email. The wider set of 28 links rests on an assumption (spec 2.5) and is deliberately not used to score signals. Assume a link, then measure a signal against it = circular.

## Short version

Two anchors carry the matching. Everything else is fallback or noise.

| Anchor | Joins | Reach |
|---|---|---|
| exact email | BookIT <-> HubSpot | 21 pairs |
| cabin + stay window | LS Retail -> BookIT | 53 of 57 rows |

Anchor gaps, and what fills them:

- No email on either side: repaired name, if unique. Only 21 of 32 bookings reach HubSpot by email, so 11 bookings need the fallback. Not a corner case.
- No cabin on the transaction (4 rows): first name + stay window.
- Name matches but is not unique (both Anna Larsens): nothing. Flag it.

Rest of this document is why the other candidate signals were rejected.

## Signal discriminative power

`true` = agreement rate on the 21 known-true pairs. `base` = the same rate on the 971 non-matching cross pairs. A signal is only useful when true >> base.

| Signal | True | Base | Lift | Verdict | Note |
|---|---|---|---|---|---|
| exact normalized name | 90% | 0.9% | 97.61x | **keep** | primary L2 rule |
| surname only | 90% | 1.8% | 51.68x | **keep** | blocking key, not a decision rule |
| first initial + surname | 90% | 0.9% | 97.61x | **keep** | blocking key |
| phone country code vs nationality | 19% | 32.7% | 0.58x | **reject** | first estimated at 4/21 |
| marketing contact before check-in | 100% | 92.8% | 1.08x | **reject** | only untested signal that could split the two Anna Larsens |

### Nationality is not phone country code

BookIT has `nationality` (SE/NO/DK). HubSpot has a phone prefix (+46/+47/+45). They look like the same fact. They are not. The prefix agrees on 19% of true pairs and 33% of non-matching pairs. That looks anti-correlated, and at this sample size it is not. 4 of 21 against a 32.7% base is a one-sided binomial p of 0.13, so the signal is uninformative rather than inverted. Either way it stays out of the score, and it must not be used to 'fix' a nationality.

### Marketing contact date looks decisive

Every true pair has the contact before check-in (offsets -90 to -11 days, median -56). Then measure the baseline: 93% of non-matching pairs satisfy it too, because every marketing date in the file precedes almost every stay. Lift 1.08x. This was the only untested signal that could have split the two Anna Larsens. It cannot.

## Email local part as a name repair source

43 of 50 emails have a local part matching the name exactly. The disagreements are the interesting part.

| Recorded name | Email local part | Token | Email says |
|---|---|---|---|
| Camilla Strnad | `camilla.strand` | `Strnad` | `strand` |
| Mikael Svnesson | `mikael.svensson` | `Svnesson` | `svensson` |
| Mikael Sevnsson | `mikael.svensson` | `Sevnsson` | `svensson` |
| Camilla Stradn | `camilla.strand` | `Stradn` | `strand` |

Both surname-bearing systems misspell the same surname, and misspell it differently. Name-to-name fuzzy matching is weak between two corruptions, and there is no third opinion: LS Retail records first name only. Two of three sources carry the surname and both are wrong.

Every corrupted name is spelled correctly in its own email address. So email is a join key and a name repair source. A further 3 disagreements are abbreviations (`m.karlsson`, `pernille.r`). Those are not errors and must not be 'repaired'.

Repair is guarded on similarity, because a shared address is not evidence of a name. The typos above score 0.83 to 0.88 against their email spelling. An unrelated name in a household address ("Anna Berg" booking with `nils.berg@gmail.com`) scores 0.25. `MIN_REPAIR_RATIO` is 0.6, in the middle of that gap. Unguarded, that booking repaired to `nils berg` and matched HubSpot's Nils Berg at 0.90.

## Cabin + stay window

The second anchor. Cabin alone is not a key: cabin 6208 is reused by Marcus Berg and Nils Berg, same surname, different weeks. Cabin plus the stay window is a key.

- 53 of 57 transactions resolve this way.
- 0 land in two overlapping stays, so the key is unambiguous here.
- 4 have no cabin at all and fall back to first name + window.

### The window is closed at both ends, on purpose

14 transactions land exactly on a check-in or check-out date. Writing it half-open, `[checkin, checkout)`, silently drops 6 of them. That is the whole difference between the anchor working and the anchor quietly leaking guests on their last day.

## Blocking keys

Pair completeness (recall) and reduction ratio against all 32 x 31 = 992 candidate pairs.

| Key | Blocks | Comparisons | Reduction | Recall |
|---|---|---|---|---|
| email exact | 21 | 21 | 97.9% | 100% |
| full name | 25 | 28 | 97.2% | 90% |
| surname | 22 | 36 | 96.4% | 90% |
| initial+surname | 25 | 28 | 97.2% | 90% |
| full name, repaired from email | 27 | 30 | 97.0% | 100% |

Name blocking alone loses 10% of true pairs: the two typo pairs share no name key. Repair names from the email local part first and recall goes to 100% at the same reduction. That is the scaling recommendation in one line: repair, then block on email and repaired name.

## Signals rejected, with reasons

### Surname morphology vs nationality

Predicts nationality at 94% (15/16). Accurate, and useless for matching: HubSpot has no nationality field, so the signal predicts a value that exists on one side only. Accurate and inapplicable are different things.

### Cabin adjacency

Generates traps. Adjacent cabins hold 4021/4022 (two different Anna Larsens) and 3067/3068 (Elisabeth and Linnea Holm). Every name collision in the file sits next door to its twin. Deck is the leading digit and relates to neither nationality nor stay length.

### Transaction spend and store profile

Cannot cross to HubSpot, which holds no transaction data. Usable only inside LS Retail, where cabin plus stay window already resolves 53 of 57 rows with zero ambiguity. No headroom.

## Records with no counterpart

Not every record has a partner. Forcing one is the failure the case tests for.

- **CRM only, never sailed** (3): Aleksander Hoff, Oskar Lindberg, Pernille Rasmussen.
- **Booked, no CRM row** (4): Ida Truelsen, Kjell Bakken, Ragnhild Vik, Signe Mortensen.
- **No transaction against their cabin** (4): Fredrik Lund, Kjell Bakken, Ragnhild Vik, Tone Fredriksen. Fredrik Lund, Tone Fredriksen are recovered by the first name + window fallback. Kjell Bakken, Ragnhild Vik genuinely did not spend.
- **No cabin recorded in BookIT either** (1): Sara Jensen. Only signal is first name + date.

Kjell Bakken, Ragnhild Vik appear in one source, with no email, no CRM row and no spend. Correct output is a one-source guest.

## The brief oversells the mess

The brief promises inconsistent date formats. There are none. All 209 date values across the three files are ISO `YYYY-MM-DD`, with 0 exceptions. No date parser needed. Measured rather than assumed, because the alternative is building a parser for a problem the data does not have.

## What this changes for the matcher

1. Repair names from email local parts before any name comparison.
2. Block on email exact, then repaired full name. Recall 100% on known pairs.
3. Keep the stay window closed at both ends.
4. Do not use phone country code, marketing contact date, surname morphology or cabin adjacency as match evidence.
5. Leave one-source records unmatched. Do not build a date parser.
6. The honest prior in the ticket held: BookIT<->HubSpot shares only name, email and phone, and no new cross-source signal was found. The one gain is name repair. It improves an existing signal instead of adding one.
